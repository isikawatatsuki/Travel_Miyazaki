# トラベルチケット改修 設計とデータ移行

実施日: 2026-07-25

## 1. 何を変えたか

トップページを「特定の旅行のホーム」から「チケット一覧」に変更し、作成・参加した旅行を
トラベルチケットとして扱う構造にした。既存の予定・お金・持ち物・共有・写真は削除せず、
チケットを選んだ後の画面としてそのまま残している。

## 2. 中心的な設計判断：チケットの実体

### 変更前の問題

アプリには2つの入れ物が並列に存在し、互いに紐付いていなかった。

- `trips: TravelProfile[]` … 端末内の旅行スナップショット
- `groups: Group[]` … サーバー同期される共有グループ

そしてライブな `SharedState` は常に**1つだけ**で、両者がそれを入れ替えていた。
`activeGroup` はチケットと独立していたため、**グループに参加した状態で旅行を切り替えると、
次の編集時にそのグループのサーバーデータが別の旅行の内容で上書きされた。**

### 採用した構造

チケット = 旅行。共有グループは**任意の紐付け**として持つ。

```ts
type Ticket = TravelProfile & {
  themeColor: string;
  completedAt?: string;   // 手動で完了にした時刻
  groupId?: string;       // 共有中のみ
  joinCode?: string;
  readToken?: string;
  editToken?: string;
};
```

これにより：

- グループを作っていない端末内だけの旅行も、チケットとして一覧に残る
- ライブ状態は常に「アクティブなチケット」に属し、同期先はそのチケットの `groupId` に限定される
- 上書きバグが構造的に解消される（`switchTrip` が `activeGroup` を必ずチケット由来の値へ差し替える）

### 却下した案

- **グループ＝チケット**：実装は最も単純だが、グループ未作成の旅行がトップページから消える。既存ユーザーのデータが見えなくなるため不採用。
- **両方を別種のチケットとして併記**：移行は安全だが、同じ旅行が2枚のチケットに見える状態が起きうる。上書きバグも残る。

## 3. データ移行

### 方針

**旧キーは削除しない。** 移行結果は新しいキー `tripShioriTickets` へ書くため、失敗しても
旧キー（`tripShioriTrips` / `tripShioriGroups` / `tripShioriGroup`）から作り直せる。

### 対応付けの手順（`migrateToTickets`）

グループと旅行の対応関係はどこにも保存されていないため、確実な情報から順に推測する。

1. `tripShioriTickets` が既にあればそれを返す（二度目の移行で作り直さない）
2. 既存の `trips` をすべてチケット化し、順番に応じたテーマカラーを割り当てる
3. `activeGroup` は `activeTripId` の旅行に紐付ける（唯一確実に分かる対）
4. 残ったグループは**名前の一致**で紐付ける
5. それでも余ったグループは、そのグループ自身の `state` から新しいチケットを生成する

手順5があるため、**端末に旅行が無いグループのデータも失われない。**

### 影響範囲

| 対象 | 影響 |
|------|------|
| 端末内の旅行 | すべてチケットとして残る。初期テーマカラーが付く |
| 共有グループ | チケットへ紐付く。参加コード・トークンを引き継ぐ |
| 参加コード | 変更なし。6桁コードの発行・参加はサーバー側も含めて無改修 |
| ログイン復旧 | 変更なし。復元したグループが新しいチケットとして増える |
| サーバー / D1 | **スキーマ変更なし。API も無改修** |
| 予約番号・添付 | 従来どおり端末ローカルのみ |

サーバーを一切触っていないため、**旧バージョンのアプリを開いている端末と併存できる。**

## 4. 経路に使う座標

`ScheduleItem` に `inRoute?: boolean`（未設定はON）と `lat?` / `lng?` を追加した。

座標の取得は**外部APIを使わない**。

1. `lat` / `lng` が保存されていればそれを使う
2. 無ければ `mapUrl` から正規表現で抽出する（`@lat,lng` / `!3d…!4d…` / `?q=lat,lng`）
3. それでも取れない予定は経路から除外し、地図の詳細パネルに名前を列挙して知らせる

ユーザーは既にGoogleマップのURLを貼る運用をしているため、手順2で大半が埋まる。
手入力欄は座標が取れない場合のみ表示する。

経路の線は既存の `HeroRouteMap` と同じベジェ曲線で地点を順に結ぶ。道路に沿った経路は
ルーティングAPI（有料または本番利用禁止）が必要になるため採用していない。

- 全体表示：完了したチケットの経路を統一色 `#4a6b8a` で重ねる
- 選択時：そのチケットのテーマカラーで1本だけ表示し、範囲を自動調整する

## 5. 確認結果

`npm run typecheck` / `npm test`（22件）/ `npm run build` すべて通過。

ブラウザ（実データ）で確認した項目：

- チケット一覧が表示され、既存の旅行が移行されている
- チケットを選ぶと従来の旅行ホームが開き、下部ナビと設定が戻る
- ヘッダーの「チケット一覧」から常に戻れる
- 旅の地図で経路が描画される。チケット選択でテーマカラー1本に切り替わり範囲が調整される
- 座標が取れない予定6件が「経路から外した予定」として列挙される
- 地図URLを貼ると座標ヒントが「地図に表示できます」に変わり、手入力欄が消える
- 390x844（モバイル）と1200px（PC）の両方でレイアウトが成立する

## 6. トップページのデザイン

- 背景は青空のグラデーションと、CSSで描いた雲4つを横に流すアニメーション
- 雲は `prefers-reduced-motion: reduce` で停止し、静止位置へ散らす
- 雲は装飾なので `aria-hidden` で支援技術から隠し、固定レイヤー（`z-index: -1`）に置いて操作を妨げない
- アプリ名は「Tabilog」のみ。説明文は削除し、チケットそのものを主役にした
- 「新しいチケットを作る」「参加コードで参加する」は `<details>` で折りたたむ
- ログインはヘッダーへ移動（チケット一覧と旅の地図でのみ表示）

## 7. 残っている課題

- **経路は直線。** 道路に沿わせるにはルーティングAPIが必要だが、今回は不要と判断した
- **`sortTickets` は毎回全チケットを走査する。** 数十枚までは問題ないが、増えたらメモ化する
  （`ponytail:` 相当の割り切り）
- 旧キー `tripShioriTrips` は残したままなので、移行が安定したと判断できた時点で削除してよい
- 地図の詳細から飛べるのは写真（`#album`）と共有メモ（`#share`）まで。個別の写真1枚を指定して開くことはできない
