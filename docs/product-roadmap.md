# 旅のしおり 機能棚卸し

## 現在の基盤

- 旅の基本設定：旅行名、日程、出発・到着時刻、交通、宿泊先
- 日別予定：時刻未定を含む追加・編集・削除、地図リンク
- 地図：出発地から宿泊先までの経路、住所検索
- 予算：交通・宿泊・朝食・お土産・追加項目
- 立替精算：メンバー、支払った人、均等割り、送金先の算出
- 準備：持ち物の追加・完了・削除
- 共有：グループ作成・参加・切替、共有メモ、自動同期、更新競合の検出（409）
- 予約情報：種別・日時・期限・メモ・添付（※予約番号と添付は端末ローカルのみ。同期されない）
- 写真アルバム：撮影・選択した写真の追加、キャプション、日付・場所
- 変更履歴とやり直し：セクション単位の更新履歴、直前の変更を元に戻す
- 複数旅行：旅行の作成・切り替え・アーカイブ・復元
- PWA：ホーム画面への追加、オフライン時の基本表示

機能は現時点で14系統あり、これを下部ナビ5枠と設定ドロワーに圧縮しています。**機能の総量そのものが最大のUX課題**という認識で、以降の追加は「既存機能を分かりやすくするもの」を優先します。

## 画面の役割と流れ

旅行中に最初に開くホームを入口にして、確認から編集へ自然に進める構成にしています。

1. ホーム：日付、次の予定、移動、宿、参加人数、1人あたりの目安を確認
2. 予定：日ごとの予定を編集し、移動経路とSTAYの住所を地図で開く
3. お金：予算の調整、追加項目、お土産、誰が払ったか、精算結果を管理
4. 持ち物：全員で使うチェックリストを追加・完了・削除
5. 共有：メンバー登録、参加グループの切替、共有メモを管理
6. 設定：旅行名、日程、交通、宿、PWA追加を管理

人数は共有ページのメンバーを唯一の基準にし、ホームの人数表示、旅費合計、1人あたりの予算、立替精算へ連動させます。計算ロジックは `src/derived.ts` に集約しています。

## 既知の弱点

1. **データの持ち主が端末** — localStorage の editToken が唯一の鍵。ブラウザデータを削除するか機種変更すると復旧手段がない
2. **機能の発見性** — 14系統が5枠のナビに圧縮されており、初回利用者は自力で全体像を掴めない
3. **予約番号と添付が同期されない** — 意図的な設計だが、UI上どこにも書かれていないため「同期されているつもり」の誤解を生む
4. **アルバムの容量** — 写真1枚あたり最大800KB、リクエスト全体で4MBの上限。枚数が増えると同期が413で失敗する
5. **`SharedState.spots`** — 常に空配列で、読み出す箇所が存在しない。削除対象

## 次にやること

### 優先度 A：今のユーザーに効く

1. **チュートリアル（折りたたみヘルプ）** — 弱点2への対処。→ `docs/account-onboarding-spec.md` B章
2. **アカウント登録（Google OAuth）** — 弱点1への対処。→ 同 A章
3. **予約情報の保存範囲の明示** — 弱点3への対処。表記を1箇所足すだけ
4. `spots` の削除 — 弱点5。3ファイルから消すだけ

1と2は独立しているので、1を先に出してよい。効果が出るのが早いのは1。

### 優先度 B：安心して共有するための基盤

1. 共有権限：閲覧のみと編集可能を分ける（`group_members.role` に受け皿を用意済み）
2. JSONバックアップ：旅行データの書き出し・読み込み
3. オフライン更新キュー：圏外で編集した内容を復帰後に送信
4. アルバムの保存先を R2 へ逃がす（弱点4）

### 優先度 C：旅行前と旅行中の便利機能

1. 通知：出発、チェックイン、予約時刻の前に知らせる
2. 行き先候補：地図検索した場所を保存し、投票して予定へ追加する
3. 天気と運行情報：旅行日と場所に合わせて確認する
4. 緊急情報：保険、連絡先、病院、紛失時のメモ

### 優先度 D：旅行後

1. 旅の記録：予定を「行った場所」へ変換し、感想を残す
2. 旅行テンプレート：過去の旅行を複製して別の旅行を作る

**優先度 C 以降を着手する前に、必ず弱点2（発見性）が解決しているか確認すること。** 機能を足すたびに弱点2は悪化する。

モバイルの下部ナビは5項目に固定し、設定は右上へ分離する方針を維持します。ナビを6枠目に増やす提案が出たら、それは既存のどこかに畳めないかを先に検討します。
